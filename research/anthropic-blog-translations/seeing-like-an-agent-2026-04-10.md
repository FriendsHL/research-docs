## 概述

构建 Agent 最难的部分之一是**设计它的工具**。

Claude 完全通过调用工具来执行操作，但在 Claude API 中可以用 bash、skills、code execution 等原语以多种方式构造工具。那么，如何为 Agent 设计工具？你是给它一个通用的工具（如 bash 或代码执行），还是给五十个专用工具，每个对应一个用例？

把自己想象成模型：想象你被要求解决一道难题。你希望用什么工具来解决？这取决于你自己的技能水平！

- 纸是最低配，但你会被手动计算所限制
- 计算器更好，但你需要知道如何操作高级选项
- 电脑最快最强，但你需要知道如何编写和执行代码

这是设计 Agent 工具的有用框架。你需要根据 Agent 自身的能力来塑造工具。但你怎么知道这些能力是什么？你需要关注、读取输出、实验。你需要学会**像 Agent 一样思考**。

如果你在构建 Agent，你会面临和我们一样的问题：**何时添加工具、何时移除工具、如何区分两者**。以下是我们构建 Claude Code 时如何回答这些问题，包括我们最初犯错的地方。

## 改进询问机制：AskUserQuestion 工具

构建 AskUserQuestion 工具时，我们的目标是提高 Claude 提问的能力（通常称为 elicitation）。

虽然 Claude 可以直接用纯文本提问，但我们发现回答这些问题感觉浪费时间。如何减少这种摩擦，增加用户和 Claude 之间沟通的带宽？

### 尝试 1：修改 ExitPlanTool

我们首先尝试的方法是在 ExitPlanTool 中添加一个参数，附带一个问题数组和计划。这是最容易实现的修复，但让 Claude 感到困惑，因为我们同时要求提供计划和关于计划的问题。如果用户的答案与计划冲突怎么办？Claude 需要调用两次 ExitPlanTool 吗？我们知道这个方案不行，于是回到重新设计。

### 尝试 2：更改输出格式

接下来，我们尝试更新 Claude 的输出指令，使用稍加修改的 markdown 格式来提问。例如，我们可以让它输出带括号的选项列表。然后我们可以解析并格式化这些内容为 UI。

Claude 通常能产生这种格式，但不可靠。它会附加额外的句子、丢弃选项，或完全放弃结构。进入下一个方法。

### 尝试 3：AskUserQuestion 工具

最终，我们创建了一个工具，Claude 可以在任何时候调用，但在 plan 模式下特别提示它调用。当工具触发时，我们会显示一个模态框来展示问题，并阻塞 Agent 循环直到用户回答。

这个工具让我们能够提示 Claude 输出结构化内容，并帮助确保 Claude 给用户多个选项。它还给了用户组合功能的方式，例如在 Agent SDK 中调用它或在 skills 中引用它。

最重要的是，Claude 似乎喜欢调用这个工具，我们发现它的输出效果很好。毕竟，即使设计得最好的工具，如果 Claude 不知道如何调用它，也不会起作用。

## 随能力更新：Tasks 和 Todos

当我们最初发布 Claude Code 时，我们意识到模型需要一个 todo 列表来跟踪进度。Todo 可以在开始时写入，然后在模型完成工作时勾选。为此，我们给 Claude 提供了 TodoWrite 工具，可以写入或更新 Todo 并展示给用户。

但即使如此，我们经常看到 Claude 忘记它要做什么。为了适应，我们每 5 轮插入系统提醒，提醒 Claude 它的目标。

随着模型改进，它们发现 todo 列表是一种限制。收到 todo 列表的提醒让 Claude 觉得它必须坚持列表，而不是在需要改变方向时修改它。我们还发现 Opus 4.5 在使用 subagents 方面好得多，但 subagents 如何在共享 todo 列表上协调？

看到这一点，我们用 **Task 工具**替换了 TodoWrite 功能。Todo 侧重于让模型保持在轨道上，而 tasks 帮助 agents 相互交流。Tasks 可以包含依赖项、在 subagents 之间共享更新，模型可以修改和删除它们。

随着模型能力增强，你的模型曾经需要的工具现在可能正在限制它们。重新审视以前关于需要哪些工具的假设很重要。这也是为什么支持一组具有相似能力配置的小模型很有用。

## 设计搜索界面

我们构建的最重要的工具是让 Claude 找到自己的上下文。

当 Claude Code 首次内部发布时，我们使用 RAG：向量数据库会预索引代码库，然后 harness 会在每次响应前检索相关片段并交给 Claude。虽然 RAG 强大且快速，但它需要索引和设置，在许多不同环境中可能很脆弱。最重要的是，Claude 是被给予上下文，而不是自己找到上下文。

但是，如果 Claude 能在网上搜索，为什么不能在代码库中搜索？通过给 Claude 提供 Grep 工具，我们可以让它搜索文件并自己构建上下文。

随着 Claude 变得更聪明，当给予正确的工具时，它越来越擅长构建自己的上下文。当我们引入 **Agent Skills** 时，我们正式提出了**渐进式披露**（progressive disclosure）的想法，允许 agents 通过探索逐步发现相关上下文。

Claude 现在可以读取 skill 文件，这些文件可以引用模型可以递归读取的其他文件。事实上，skills 的常见用法是向 Claude 添加更多搜索能力，比如给如何使用 API 或查询数据库的指令。

在一年内，Claude 从不太能够构建自己的上下文，到能够在多层文件中进行嵌套搜索以找到它需要的确切上下文。

渐进式披露现在是我们用来添加新功能而不添加工具的常用技术。在下一节中，我们解释原因。

## 渐进式披露：Claude Code Guide Agent

Claude Code 目前有约 20 个工具，我们的团队经常重新审视是否需要所有这些工具才能让 Claude 发挥最大效力。添加新工具的门槛很高，因为这给模型多了一个选项来思考。

例如，我们注意到 Claude 不太了解如何使用 Claude Code。如果你问它如何添加 MCP 或什么是斜杠命令，它无法回答。

我们本可以把所有这些信息放在 system prompt 中，但鉴于用户很少问这会增加上下文腐臭，并干扰 Claude Code 的主要工作：写代码。

相反，我们尝试了渐进式披露：我们给 Claude 一个文档链接，它可以在需要时加载和搜索。这有效了，但 Claude 会拉取大块文档来找到用户一句话就能得到的答案。

于是我们构建了 **Claude Code Guide**——一个子 agent，当用户问关于 Claude Code 本身时，Claude 会调用它。子 agent 在自己的上下文中做文档搜索，有详细的搜索指导和提取内容，只把答案传回。主 agent 的上下文保持干净。

虽然这不是完美方案（当你问它如何设置自己时，Claude 仍然可能困惑），我们能够在不添加新工具的情况下向 Claude 的行动空间添加内容。

## 像 Agent 一样思考是一门艺术，不是科学

为模型设计工具既是艺术也是科学。它很大程度上取决于你使用的模型、agent 的目标和它运行的环境。

**我们最好的建议？**

- 经常实验
- 读取输出
- 尝试新事物
- 最重要的是，**试着像 Agent 一样思考**

## 我的总结与理解

### 核心洞察

这篇文章深入探讨了**工具设计**的艺术，而不是简单地堆砌工具。关键点：

1. **能力匹配**：工具要适配模型当前的能力水平，不是越多越好
2. **渐进式披露**：不要把所有东西都塞进 system prompt，按需加载
3. **持续迭代**：随着模型能力提升，曾经有用的工具可能变成限制
4. **观察行为**：通过阅读模型输出来理解它如何思考

### 三个经典案例详解

1. **AskUserQuestion**
   - 问题：如何让 Claude 更有效地提问？
   - 三次迭代：修改 ExitPlanTool → 改输出格式 → 创建专用工具
   - 教训：最自然的方案不一定是最好的，需要通过实验验证

2. **Tasks 替代 Todos**
   - 问题：Claude 忘记任务、收到提醒反而被束缚
   - 解决：用 Task 工具替代 TodoWrite，支持依赖和共享
   - 教训：模型能力进化时，工具语义也可能从帮助变成限制

3. **Claude Code Guide**
   - 问题：Claude 不了解自己（如何添加 MCP 等）
   - 解决：不塞进 system prompt，而是建一个子 agent 来查文档
   - 教训：渐进式披露比一次性灌输更有效

### 对我们的启发

OpenClaw 在设计工具时也可以借鉴：

1. **不是工具越多越好**
   - 每个新工具都是模型需要考虑的选项
   - 门槛要设高，避免工具膨胀

2. **渐进式披露的具体做法**
   - 基础功能默认提供
   - 高级功能通过 skill 文件按需加载
   - 文档查询用子 agent 而非直接写入 prompt

3. **定期审视工具的有效性**
   - 模型能力在变，工具设计也要跟着变
   - 观察模型实际使用行为，而非假设它应该如何

### 可操作的建议

- [ ] 建立工具使用的监控和反馈机制
- [ ] 为每个新工具设置明确的添加理由和评估标准
- [ ] 定期（每季度）审查现有工具是否仍然必要
- [ ] 使用 subagent 隔离复杂的辅助功能

---

**一句话总结**：设计 Agent 工具的核心是**「像 Agent 一样思考」**——关注模型实际如何使用工具，而不是我们觉得它应该用什么。
