## 概述

我们发布了 `/usage`，一个新的 slash 命令帮助你了解 Claude Code 的使用情况。这个功能来自于与客户的多次对话。

在这些通话中反复出现的是：用户管理 session 的方式有很多差异，特别是我们的 Claude Code 更新到 100 万上下文之后。

## 上下文、压缩和上下文腐臭速成班

上下文窗口是模型在生成下一个响应时能"看到"的一切。它包括你的 system prompt、到目前为止的对话、每次工具调用及其输出，以及每次读取的文件。Claude Code 有 100 万 token 的上下文窗口。

不幸的是，使用上下文对性能有轻微影响，这通常被称为**上下文腐臭**（context rot）。上下文腐臭是指随着上下文增长，模型性能下降的观察结果，因为注意力分散在更多 token 上，更旧的不相关内容开始分散当前任务的注意力。

上下文窗口是硬切分，所以当你接近上下文窗口的末尾时，你一直在处理的任务会自动总结为更小的描述，模型在新上下文窗口中继续工作。我们称之为**压缩**（compaction）。你也可以自己触发压缩。

## 每个 turn 都是分支点

假设你刚刚让 Claude 完成某事，它完成了——你現在在上下文中有一些信息（工具调用、工具输出、你的指令），对于接下来要做什么，你有很多选择：

- **Continue**：在同一个 session 中发送另一条消息
- **Rewind (esc esc)**：跳回上一条消息并从那里重新尝试
- **Clear**：开始一个新 session，通常带有你从刚才学到的东西中提炼的 brief
- **Compact**：总结到目前为止的 session 并在总结的基础上继续
- **Subagents**：将下一块工作委托给一个有自己干净上下文的 agent，只把它的结果拉回来

虽然最自然的做法是继续，但其他四个选项存在是为了帮助你管理上下文。

---

## 何时开始新 Session

何时保持长时间运行的 session vs 开始新的？我们的经验法则是：**当你开始新任务时，你也应该开始新 session**。

虽然 100 万上下文窗口意味着你现在可以更可靠地做更长的任务，例如从头构建一个全栈应用，但可能会发生上下文腐臭。

有时你可能做相关任务，其中一些上下文仍然是必要的，但并非总是如此。例如，为你刚刚实现的功能写文档。虽然你可以开始新 session，但 Claude 必须重新读取你刚刚实现的文件，这会更慢且更昂贵。

---

## 回退而不是纠正

在 Claude Code 中，双击 Esc（或运行 `/rewind`）让你跳回任何之前的消息并从那里重新 prompt。那一点之后的消息会从上下文中删除。

Rewind 通常是更好的纠正方法。例如，Claude 读取五个文件，尝试一种方法，但它不工作。你的本能可能是输入"那不行，试试 X"。但更好的做法是 rewindo 到文件读取之后，用你学到的知识重新 prompt。"不要使用 approach A，foo 模块没有暴露那个——直接用 B。"

你也可以使用"从这里总结"或 `/rewind` slash 命令让 Claude 总结它的学习并创建一个交接消息，就像来自未来的 Claude 给它的过去迭代的一条消息，尝试了一些但没有成功。

---

## 压缩 vs 启动新 Session

一旦 session 变长，你有两种方式删除无关上下文：`/compact` 或 `/clear`（然后重新开始）。它们感觉相似但行为非常不同。

Compact 要求模型总结到目前为止的对话，然后用该总结替换历史。它是有损的，但你不必自己写什么，Claude 可能更彻底地包含重要的学习或文件。你也可以通过传递指令来引导它（`/compact focus on the auth refactor, drop the test debugging`）。

用 `/clear` 你写下重要的东西（"我们正在重构 auth 中间件，约束是 X，重要的文件是 A 和 B，我们已经排除了 approach Y"）然后干净地开始。它需要更多工作，但 resulting 上下文是你决定相关的。

---

 ## 什么导致糟糕的自动压缩

如果你运行很多长时间运行的 session，你可能已经注意到有时压缩可能特别糟糕。在这种情况下，我们经常发现当模型无法预测你的工作方向时，糟糕的压缩可能会发生。

在上面的例子中，自动压缩在长调试会话后触发，总结了调查，你下一条消息是"现在修复我们在 bar.ts 中看到的另一个警告"。但因为 session 专注于调试，另一个警告可能从总结中丢失。

这特别困难，因为由于上下文腐臭，模型在压缩时处于最低智能点。有了 100 万上下文，你有时间主动 `/compact` 并描述你想做什么。

---

## Subagents 和干净的上下文窗口

Subagents 很好地工作，当你事先知道一块工作会产生很多你不再需要的中间输出时。

当 Claude 通过 Agent 工具生成 subagent 时，那个 subagent 得到它自己的干净上下文窗口。它可以做尽可能多的工作，然后综合它的结果，这样只有最终报告回到父 agent。

我们在 Anthropic 使用的心理测试：我会再次需要这个工具输出，还是只需要结论？

虽然 Claude Code 会自动调用 subagents，但你可能想明确告诉它这样做。例如，你可能想告诉它：

- "生成一个 subagent 来根据以下 spec 文件验证这个工作的结果"
- "分出一个 subagent 读取这个其他代码库并总结它如何实现 auth flow，然后你以相同方式实现它"
- "分出一个 subagent 基于我的 git 更改写这个功能的文档"

## 总结表

| 情况 | 考虑使用 | 原因 |
|------|----------|------|
| 相同任务，上下文仍然相关 | Continue | 窗口中的一切仍然是承重的；不要花钱重建它 |
| Claude 走错了路 | Rewind (double-Esc) | 保留有用的文件读取，丢弃失败的尝试，用你学到的重新 prompt |
| 任务中途但 session 因陈旧的调试/探索而臃肿 | `/compact <hint>` | 低努力；Claude 决定什么重要。如需要用指令引导它 |
| 开始真正新任务 | `/clear` | 零腐臭；你精确控制什么向前传递 |
| 下一步会产生很多输出，你只需要结论（代码库搜索、验证、文档编写） | Subagent | 中间工具噪音留在子上下文；只有结果回来 |

## 我的总结与理解

### 核心概念

这篇文章深入解释了**上下文管理**的艺术：

1. **上下文腐臭**：上下文越长，模型越"笨"
2. **压缩**：自动总结，但可能丢失重要信息
3. **Subagents**：干净的子上下文，只传回结论
4. **每个 turn 都是分支点**：随时可以分叉、回顾、重新开始

### 五个工具的使用场景

| 工具 | 什么时候用 | 为什么 |
|------|------------|--------|
| Continue | 同一任务，上下文仍然有用 | 窗口中的一切仍是承重的 |
| Rewind (Esc Esc) | Claude 走错路 | 保留有用的文件读取，丢弃失败的尝试 |
| /compact | Session 臃肿，有陈旧调试/探索 | 低努力；Claude 决定什么重要 |
| /clear | 开始真正新任务 | 零腐臭；你控制精确度 |
| Subagent | 下一步产生大量输出，只需要结论 | 中间噪音留在子上下文 |

### 上下文腐臭的应对策略

1. **预防为主**
   - 一次性给足上下文（任务描述、约束、文件位置）
   - 避免在多个 turn 中逐渐补充信息

2. **及时压缩**
   - 不要等 auto compact（可能丢失重要信息）
   - 主动 /compact 并给 hint

3. **适时分叉**
   - 用 side chat 问临时问题
   - 用 subagent 隔离大量中间输出

4. **定期清理**
   - 新任务开新 session
   - 复杂任务拆分成多个 session

### 百万上下文的使用场景

100 万 token 上下文让这些成为可能：
- 从头构建全栈应用
- 跨多个文件的大型重构
- 长期运行的 Agent 任务

但也更容易遇到上下文腐臭，需要更主动地管理。

### 对我们的启发

在设计 Agent 系统时：
- [ ] 不要让上下文无限增长
- [ ] 适时用 subagent 隔离大量中间输出
- [ ] 学会判断何时该开新 session
- [ ] 建立上下文监控机制（/usage）
- [ ] 给用户清晰的控制选项（compact/clear/rewind）

### 一个核心原则

**把 Claude 当作能干的工程师委托，而不是配对程序员指导**

- upfront 详细描述任务
- 减少中间干预
- 让它在必要时主动压缩或分叉

---

**一句话总结**：上下文管理是 **"在保持记忆"和"避免腐臭"之间的平衡艺术**。
