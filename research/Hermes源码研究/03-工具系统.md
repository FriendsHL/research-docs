# 工具系统源码解析

## 一、先给结论

Hermes 的工具系统可以用一句话概括：

```text
工具文件自己注册工具；
toolset 决定哪些工具开放给模型；
模型返回 tool_call；
agent loop 执行工具；
工具结果作为 role=tool 消息塞回上下文；
模型下一轮继续看结果。
```

主链路是：

```text
tools/*.py
  -> registry.register(...)

tools/registry.py
  -> 保存 schema、handler、toolset、check_fn

toolsets.py
  -> 定义工具分组，比如 file、terminal、browser、hermes-cli

model_tools.py::get_tool_definitions()
  -> 按 toolset 过滤，生成给 LLM 的 OpenAI tool schema

LLM response
  -> assistant.tool_calls

run_agent.py::_execute_tool_calls()
  -> 决定串行还是并行
  -> 执行工具
  -> append role=tool result

下一轮 API call
  -> 模型看到 tool result，继续推理或最终回答
```

所以工具系统不是一个单独的“工具调用函数”，而是分布在三块：

```text
registry：工具有哪些
toolsets：哪些工具当前可用
agent loop：什么时候执行、怎么执行、结果怎么回填
```

## 二、一个最简单的例子：read_file

用户问：

```text
帮我看看 run_agent.py 里的主循环。
```

模型第一次 API call 可能返回：

```python
assistant:
  tool_calls = [
    {
      "id": "call_abc",
      "function": {
        "name": "read_file",
        "arguments": "{\"path\":\"run_agent.py\",\"offset\":10000,\"limit\":200}"
      }
    }
  ]
```

Hermes 做的事：

```text
1. 解析 tool_call
2. 找到工具名 read_file
3. JSON 解析 arguments
4. 调用 read_file handler
5. 拿到文件内容 result
6. append 一条 tool message
```

messages 变成：

```python
assistant:
  tool_calls = [call_abc: read_file(...)]

tool:
  tool_call_id = "call_abc"
  content = "run_agent.py 对应片段..."
```

下一轮模型看到：

```text
我刚才要求读 run_agent.py。
现在 tool result 里有源码片段。
我可以基于它继续分析。
```

这就是 Hermes tool loop 的基本形态。

## 三、工具是怎么注册的

每个工具文件在模块顶层调用：

```python
registry.register(
    name="read_file",
    toolset="file",
    schema=READ_FILE_SCHEMA,
    handler=_handle_read_file,
    check_fn=_check_file_reqs,
    emoji="📖",
    max_result_size_chars=float("inf"),
)
```

真实例子在 `tools/file_tools.py`：

```python
registry.register(name="read_file", toolset="file", schema=READ_FILE_SCHEMA, handler=_handle_read_file, check_fn=_check_file_reqs, emoji="📖", max_result_size_chars=float('inf'))
registry.register(name="write_file", toolset="file", schema=WRITE_FILE_SCHEMA, handler=_handle_write_file, check_fn=_check_file_reqs, emoji="✍️", max_result_size_chars=100_000)
registry.register(name="patch", toolset="file", schema=PATCH_SCHEMA, handler=_handle_patch, check_fn=_check_file_reqs, emoji="🔧", max_result_size_chars=100_000)
registry.register(name="search_files", toolset="file", schema=SEARCH_FILES_SCHEMA, handler=_handle_search_files, check_fn=_check_file_reqs, emoji="🔎", max_result_size_chars=100_000)
```

注册信息包括：

```text
name
  -> 模型调用时用的工具名

toolset
  -> 属于哪个工具组

schema
  -> 给模型看的 JSON schema

handler
  -> 真正执行工具的 Python 函数

check_fn
  -> 判断工具当前是否可用

requires_env
  -> 需要哪些环境变量

is_async
  -> handler 是否是 async

emoji / description
  -> UI 展示用

max_result_size_chars
  -> 单个工具结果超过多大要落盘/裁剪
```

## 四、自动发现怎么做

入口在：

```text
tools/registry.py::discover_builtin_tools()
```

它不会无脑 import `tools/` 下所有文件，而是先用 AST 看文件顶层有没有：

```python
registry.register(...)
```

只有顶层有注册调用的文件才会 import。

好处：

```text
1. 避免 import 一堆工具辅助模块
2. 避免某些工具文件副作用太大
3. 工具文件只要自注册，不需要维护一个巨大 import 列表
```

`model_tools.py` import 时会触发：

```python
discover_builtin_tools()
```

然后插件工具也会加载：

```python
from hermes_cli.plugins import discover_plugins
discover_plugins()
```

MCP 工具比较特殊，不再作为 `model_tools.py` 的模块级副作用自动发现。原因是 MCP server 连接可能很慢，Gateway 在事件循环里 lazy import 时会卡住心跳。所以现在各入口启动时显式做 MCP discovery。

## 五、registry 里存了什么

`tools/registry.py::ToolRegistry` 核心字段：

```text
_tools
  -> {tool_name: ToolEntry}

_toolset_checks
  -> {toolset_name: check_fn}

_toolset_aliases
  -> MCP / plugin toolset 的别名

_generation
  -> registry 变更版本号，用来让 schema cache 失效
```

`ToolEntry` 保存：

```text
name
toolset
schema
handler
check_fn
requires_env
is_async
description
emoji
max_result_size_chars
```

dispatch 时：

```text
registry.dispatch(name, args)
  -> 找 ToolEntry
  -> 如果 is_async，用 _run_async 包一层
  -> 调 handler(args, **kwargs)
  -> handler 必须返回 JSON string
  -> 异常统一变成 {"error": "..."}
```

工具 handler 的返回值约定很重要：

```text
所有工具都应该返回 JSON 字符串。
不是 Python dict。
```

辅助函数：

```python
tool_result(success=True, data=...)
tool_error("file not found")
```

## 六、Toolset 是什么

`toolsets.py` 定义工具分组。

比如：

```text
file
  -> read_file, write_file, patch, search_files

terminal
  -> terminal, process

browser
  -> browser_navigate, browser_snapshot, browser_click, ...

skills
  -> skills_list, skill_view, skill_manage

delegation
  -> delegate_task
```

也有平台级 toolset：

```text
hermes-cli
hermes-telegram
hermes-discord
hermes-api-server
hermes-acp
hermes-gateway
```

`hermes-cli` 用的是 `_HERMES_CORE_TOOLS`，里面包括：

```text
web_search, web_extract
terminal, process
read_file, write_file, patch, search_files
vision_analyze, image_generate
skills_list, skill_view, skill_manage
browser_*
todo, memory
session_search
clarify
execute_code, delegate_task
cronjob
send_message
homeassistant tools
```

toolset 可以组合：

```python
"debugging": {
  "tools": ["terminal", "process"],
  "includes": ["web", "file"]
}
```

解析时：

```text
resolve_toolset("debugging")
  -> terminal/process
  -> 加上 web 的工具
  -> 加上 file 的工具
```

还有特殊别名：

```text
all
*
```

表示所有 toolset 的工具合集。

## 七、工具 schema 怎么给模型

入口：

```text
model_tools.py::get_tool_definitions()
```

它做几步：

```text
1. 根据 enabled_toolsets / disabled_toolsets 计算候选工具名
2. 调 registry.get_definitions(...)
3. 每个工具跑 check_fn
4. 只保留可用工具
5. 动态修改某些 schema
6. sanitize schema，适配严格 provider
7. 返回 OpenAI-format tools
```

返回格式：

```python
[
  {
    "type": "function",
    "function": {
      "name": "read_file",
      "description": "...",
      "parameters": {...}
    }
  }
]
```

这些 tools 最后进入 provider request：

```python
client.chat.completions.create(
  model=...,
  messages=...,
  tools=tool_schemas,
)
```

如果是 Anthropic、Bedrock、Codex Responses，transport 层会再把 OpenAI-format schema 转成对应 provider 的格式。

## 八、schema 不是完全静态的

`get_tool_definitions()` 里会根据当前可用工具和配置动态改 schema。

### 1. execute_code schema

`execute_code` 可以在 sandbox 里调用部分工具。它的 schema 会根据当前真实可用工具重建：

```text
如果 web_search 当前不可用，
execute_code schema 里就不能说 web_search 可用。
```

否则模型会在代码执行工具里幻想调用不存在的工具。

### 2. Discord schema

Discord 工具会根据 bot intents 和用户配置重建 schema。

比如 bot 没有 MESSAGE_CONTENT intent，就不能让模型尝试读取完整消息内容。

### 3. browser_navigate 描述

如果 `web_search` / `web_extract` 不可用，`browser_navigate` 描述里会移除：

```text
prefer web_search or web_extract
```

避免模型调用不存在的工具。

### 4. schema sanitizer

最后会跑：

```text
tools.schema_sanitizer.sanitize_tool_schemas()
```

因为有些 provider 或本地模型对 JSON schema 很严格，比如 llama.cpp 的 grammar 生成器，不接受某些云 provider 能接受的 schema 写法。

## 九、check_fn 和 requires_env

工具可以带：

```text
check_fn
requires_env
```

例子：

```text
terminal
  -> check_terminal_requirements()

Home Assistant
  -> 需要 HASS_TOKEN

browser
  -> 需要浏览器/Playwright 环境

send_message
  -> gateway 运行时才可用
```

`registry.get_definitions()` 只返回 check_fn 通过的工具。

check_fn 结果有 30 秒 TTL：

```text
_CHECK_FN_TTL_SECONDS = 30
```

原因是一些 check 很贵：

```text
Docker daemon 是否可用
Modal SDK 是否安装
Playwright 浏览器是否可用
外部服务 token 是否存在
```

长驻 CLI/Gateway 不应该每次请求都重新探测。

## 十、模型返回 tool_call 后怎么执行

主循环里进入：

```text
run_agent.py::_execute_tool_calls()
```

第一步先判断：

```text
_should_parallelize_tool_batch(tool_calls)
```

如果不能并行：

```text
_execute_tool_calls_sequential()
```

如果可以并行：

```text
_execute_tool_calls_concurrent()
```

执行完后，每个结果都 append：

```python
{
  "role": "tool",
  "content": function_result,
  "tool_call_id": tool_call.id,
}
```

下一轮 API call 会把这条 tool result 发给模型。

## 十一、Agent-level tools

有些工具虽然在 registry 里注册 schema，但不能只靠普通 `registry.dispatch()` 执行。

这些叫 agent-level tools：

```python
_AGENT_LOOP_TOOLS = {"todo", "memory", "session_search", "delegate_task"}
```

原因是它们需要 `AIAgent` 的内部状态：

```text
todo
  -> 需要 self._todo_store

memory
  -> 需要 self._memory_store，并通知 external memory provider

session_search
  -> 需要 self._session_db 和 current_session_id

delegate_task
  -> 需要 parent_agent、budget、toolsets、interrupt 继承
```

所以普通 dispatcher 里如果收到这些工具，会返回：

```json
{"error": "todo must be handled by the agent loop"}
```

真正执行在 `run_agent.py::_invoke_tool()` 或 sequential path 里。

直白说：

```text
普通工具：给 handler 参数就能跑。
agent-level 工具：必须拿到当前 agent 的脑内状态才能跑。
```

## 十二、并行工具执行

Hermes 支持同一轮多个 tool call 并行执行，但规则很保守。

并行判断：

```text
1. 只有 0/1 个 tool call
   -> 串行

2. 包含 clarify
   -> 串行

3. arguments 解析失败
   -> 串行

4. read_file/write_file/patch 这类路径工具
   -> 路径必须存在且互不重叠

5. 其他工具必须在 _PARALLEL_SAFE_TOOLS 白名单
   -> 不在白名单就串行
```

白名单：

```python
_PARALLEL_SAFE_TOOLS = {
    "ha_get_state",
    "ha_list_entities",
    "ha_list_services",
    "read_file",
    "search_files",
    "session_search",
    "skill_view",
    "skills_list",
    "vision_analyze",
    "web_extract",
    "web_search",
}
```

路径工具：

```python
_PATH_SCOPED_TOOLS = {"read_file", "write_file", "patch"}
```

永不并行：

```python
_NEVER_PARALLEL_TOOLS = {"clarify"}
```

最大 worker：

```text
_MAX_TOOL_WORKERS = 8
```

### 并行例子

模型一次返回：

```text
read_file("run_agent.py")
read_file("model_tools.py")
search_files("ContextCompressor")
web_search("Hermes Agent")
```

这些大概率可以并行，因为：

```text
read_file 路径不同
search_files 是白名单
web_search 是白名单
没有 clarify
没有未知副作用工具
```

但这个不能并行：

```text
patch("run_agent.py")
write_file("run_agent.py")
```

因为路径重叠，必须串行。

这个也不能并行：

```text
terminal("npm test")
read_file("package.json")
```

`terminal` 不在并行安全白名单里，因为它可能修改文件、启动服务、占用状态。

## 十三、并行执行怎么保证结果顺序

并行时用 `ThreadPoolExecutor`。

执行时是并行：

```text
worker 1 跑 read_file A
worker 2 跑 read_file B
worker 3 跑 web_search
```

但结果 append 回 messages 时，会按原始 tool_call 顺序：

```text
tool result 1
tool result 2
tool result 3
```

这样 provider 看到的 tool result 顺序和 assistant.tool_calls 顺序一致。

并行 worker 还要继承一些 thread-local callback：

```text
approval callback
sudo password callback
activity callback
interrupt flag
```

否则危险命令 approval、sudo prompt、Gateway heartbeat 会出问题。

## 十四、工具执行前后的安全和 hook

执行工具前：

```text
pre_tool_call hook
  -> 可以 block 工具

write_file / patch
  -> checkpoint 工作区

terminal destructive command
  -> checkpoint 工作区

tool_start_callback / tool_progress_callback
  -> UI/Gateway/TUI 展示进度
```

普通工具执行后：

```text
post_tool_call hook
  -> 观察结果和 duration_ms

transform_tool_result hook
  -> 可以替换最终 tool result

tool_complete_callback
  -> UI/Gateway/TUI 收尾
```

`terminal` 还有更早的专门 hook：

```text
transform_terminal_output
```

它发生在 terminal 工具内部默认截断/清洗之前。

## 十五、工具结果太大怎么办

工具结果进上下文前有三层保护，源码在：

```text
tools/tool_result_storage.py
tools/budget_config.py
```

### 1. 工具自己先限制

有些工具内部会自己分页、截断、限制返回数量。

比如搜索工具不会无限返回所有匹配。

### 2. 单个结果过大就落盘

如果一个工具结果超过阈值，会保存到 sandbox 临时目录：

```text
/tmp/hermes-results/{tool_call_id}.txt
```

上下文里只保留：

```text
<persisted-output>
This tool result was too large...
Full output saved to: /tmp/hermes-results/call_abc.txt
Use the read_file tool with offset and limit...

Preview:
...
</persisted-output>
```

默认阈值：

```text
DEFAULT_RESULT_SIZE_CHARS = 100_000
DEFAULT_PREVIEW_SIZE_CHARS = 1_500
```

但 `read_file` 被固定为：

```text
read_file: inf
```

原因是如果 `read_file` 自己的结果也被落盘，模型可能陷入：

```text
读文件 -> 结果太大落盘 -> 再 read_file 读落盘文件 -> 又太大落盘
```

### 3. 单轮总结果过大也会落盘

如果一轮多个工具结果加起来超过：

```text
DEFAULT_TURN_BUDGET_CHARS = 200_000
```

Hermes 会把最大的非持久化结果先落盘，直到总量降下来。

例子：

```text
一次并行调用 5 个 web_extract
每个 60K
总共 300K

单个都没超过 100K
但合起来超过 200K

=> 最大的几个结果会被保存到 /tmp/hermes-results/
=> messages 里只留 preview + 文件路径
```

这和前面压缩不同：

```text
tool_result_storage
  -> 工具结果刚回来时控制大小

context_compressor
  -> 整个会话历史太长时压缩中间历史
```

## 十六、MCP 工具怎么接进来

MCP 工具在：

```text
tools/mcp_tool.py
```

流程：

```text
连接 MCP server
读取 server tools/list
把 MCP tool schema 转成 Hermes/OpenAI schema
registry.register(...)
注册到 toolset: mcp-<server_name>
给 server_name 注册 toolset alias
```

冲突处理很保守：

```text
如果 MCP tool 名字会覆盖内置工具
  -> 跳过 MCP 工具
  -> 保留内置工具
```

这避免外部 MCP server 把 `read_file`、`terminal` 这类核心工具覆盖掉。

MCP 工具也走统一 registry，所以后面执行、schema 暴露、toolset 过滤和普通工具一致。

## 十七、Plugin 工具怎么接进来

插件通过：

```text
hermes_cli/plugins.py::PluginContext.register_tool()
```

内部也是调用：

```python
tools.registry.registry.register(...)
```

所以插件工具不会另开一套系统。

它们也有：

```text
toolset
schema
handler
check_fn
requires_env
```

`toolsets.py` 会把 registry 中动态出现的 plugin toolset 也算进去。

## 十八、execute_code 是特殊工具

`execute_code` 的作用是：

```text
让模型写一段 Python，在 sandbox 里批量调用工具。
```

它可以减少多轮 LLM/tool 往返。

例子：

```text
普通方式：
  模型调用 read_file A
  等结果
  模型调用 read_file B
  等结果
  模型调用 search_files
  等结果

execute_code：
  模型写一段 Python
  Python 里调用 read_file/search_files
  一次性返回聚合结果
```

但它能调用哪些工具，不是写死的。`get_tool_definitions()` 会根据当前 session 真实可用工具动态生成 `execute_code` schema。

## 十九、delegate_task 是特殊工具

`delegate_task` 会创建子 agent。

它不是普通 handler 能完全处理的，因为需要：

```text
parent_agent
当前 toolsets
iteration budget
interrupt propagation
credential/fallback/context
子 agent 结果回传
subagent_stop hook
```

所以它是 agent-level tool。

主循环里有统一入口：

```text
run_agent.py::_dispatch_delegate_task()
```

然后调用：

```text
tools/delegate_tool.py::delegate_task()
```

## 二十、工具系统和 Provider 的关系

Hermes 内部工具 schema 是 OpenAI-format。

但不同 provider 最终看到的不一样：

```text
chat_completions
  -> 直接传 OpenAI tools

anthropic_messages
  -> transport 转成 Anthropic input_schema

codex_responses
  -> transport 转成 Responses API function tools

bedrock_converse
  -> transport 转成 Bedrock toolConfig
```

所以工具系统本身不用关心 provider 差异。

真正关心 provider 差异的是 `agent/transports/*`。

## 二十一、一个完整 trace

以 `read_file` 为例：

```text
启动时:
  tools/file_tools.py 被 import
  registry.register("read_file", ...)

创建 AIAgent:
  get_tool_definitions(enabled_toolsets=["hermes-cli"])
  resolve_toolset("hermes-cli")
  registry.get_definitions(...)
  得到 read_file schema

API call:
  tools 传给模型

模型响应:
  assistant.tool_calls = [read_file({"path":"run_agent.py"})]

主循环:
  _execute_tool_calls()
  _should_parallelize_tool_batch()
  _execute_tool_calls_sequential() 或 concurrent()

执行:
  _invoke_tool("read_file", args)
  handle_function_call(...)
  registry.dispatch("read_file", args)
  _handle_read_file(args)

结果:
  maybe_persist_tool_result(...)
  append {"role":"tool","tool_call_id":"call_xxx","content":"..."}

下一轮:
  模型读取 tool result
  继续调用工具或最终回答
```

## 二十二、设计观察

### 1. 自注册降低维护成本

新增工具一般只需要：

```text
1. 新建 tools/xxx.py
2. 顶层 registry.register(...)
3. 加到 toolsets.py 某个 toolset
```

不用再去 `model_tools.py` 维护一个大 import 列表。

### 2. registry 和 toolset 分工清楚

```text
registry 说：工具是什么，怎么执行。
toolset 说：这次给模型开放哪些工具。
```

这让 CLI、Gateway、ACP、API Server 可以用不同工具集合。

### 3. agent-level tools 是复杂度来源

`todo/memory/session_search/delegate_task` 需要 agent 内部状态，所以工具分发不能完全统一。

这也是为什么主循环里仍然有大量工具相关代码。

### 4. 工具结果管理和压缩是两道防线

工具刚执行完：

```text
tool_result_storage 控制单个/单轮结果大小
```

会话很长以后：

```text
context_compressor 压缩中间历史
```

两者解决的问题不一样。

### 5. 并行执行提升速度，但只对安全工具开放

Hermes 没有盲目并行所有工具，而是白名单 + 路径冲突检查。

这是因为工具可能有副作用：

```text
写文件
patch 文件
terminal 改状态
clarify 等用户输入
delegate_task 创建子 agent
```

默认串行更安全。
