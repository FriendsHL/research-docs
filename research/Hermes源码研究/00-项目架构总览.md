# Hermes Agent 项目架构总览

> 研究日期：2026-04-30  
> 源码路径：`/Users/youren/myspace/hermes-agent/`

## 一、核心定位

Hermes Agent 不是单一 CLI 程序，而是一套 **Agent runtime + 多入口产品壳 + 扩展系统**。

它的核心收敛点是：

- `run_agent.py`：`AIAgent`，负责主对话循环、模型调用、工具执行、上下文/记忆/会话协调。
- `model_tools.py` + `tools/registry.py` + `toolsets.py`：负责工具 schema、可用性、toolset 分组和 tool call 分发。
- `hermes_state.py`：负责 session 持久化和历史检索。
- `hermes_cli/config.py` + `hermes_constants.py`：负责配置、profile-aware 路径和运行时 home。

围绕这个核心，Hermes 暴露了多个入口：

- classic CLI：`hermes` / `hermes chat`
- Ink TUI：`hermes --tui`
- messaging gateway：`hermes gateway`
- dashboard chat：浏览器里嵌入真实 `hermes --tui`
- ACP server：`hermes acp`
- MCP server：`hermes mcp serve`
- cron scheduler：定时 job 后台调用 agent
- batch runner / RL 环境：批量生成轨迹或训练数据

## 三、启动入口：`hermes_cli/main.py`

`hermes_cli/main.py` 是 `hermes` 命令的主入口。它最重要的职责不是直接跑 agent，而是 **在任何重型模块 import 前完成运行环境选择**。

### 1. Profile override 必须最早执行

文件开头的 `_apply_profile_override()` 会预解析 `--profile/-p`：

```text
sys.argv
  -> 找 --profile/-p
  -> resolve_profile_env(profile)
  -> 设置 os.environ["HERMES_HOME"]
  -> 从 sys.argv 移除 profile 参数
  -> 后续模块 import 时读到正确 HERMES_HOME
```

这是 profile 安全的关键，因为很多模块会在 import 时缓存路径常量。如果 `HERMES_HOME` 设置晚了，后续 session、日志、配置、skills、plugins 都可能落到错误 profile。

### 2. 早期环境初始化

`main.py` 接着做几件全局初始化：

- 加载 `~/.hermes/.env`，开发模式再 fallback 到项目 `.env`。
- 从 `config.yaml` bridge `security.redact_secrets` 到 `HERMES_REDACT_SECRETS`。
- 初始化 `hermes_logging.setup_logging(mode="cli")`。
- 读取 `network.force_ipv4` 并应用 IPv4 preference。

这些动作发生在 CLI 子命令分发前，因此 `hermes setup`、`hermes gateway`、`hermes mcp serve` 等路径都受同一套 profile/env/logging 约束。

### 3. 命令路由

`main.py` 用 argparse 挂载大量子命令：

- agent 相关：`chat`、默认无子命令、`acp`
- messaging：`gateway`
- automation：`cron`
- integration：`mcp`
- 配置：`setup`、`config`、`model`、`tools`、`skills`、`plugins`、`profile`
- 运维：`status`、`doctor`、`logs`、`update`、`uninstall`

这里还有一个性能优化点：只有 agent 类命令才预发现 MCP tools，普通配置命令不会为工具发现付出启动成本。

## 四、Agent Core：`AIAgent`

`AIAgent` 位于 `run_agent.py`，是 Hermes 的核心同步 agent loop。

### 关键公开接口

- `AIAgent.__init__(...)`
- `AIAgent.run_conversation(user_message, system_message=None, conversation_history=None, task_id=None)`
- `AIAgent.chat(message)`

`__init__()` 参数非常多，说明 `AIAgent` 是各入口共享的核心运行时，而不是 CLI 专用对象。关键参数可以分成几类：

| 类别 | 代表参数 | 作用 |
|---|---|---|
| 模型运行时 | `model` / `provider` / `api_mode` / `base_url` / `api_key` | 决定调用哪个 provider |
| 工具 | `enabled_toolsets` / `disabled_toolsets` | 决定暴露哪些工具 |
| 会话 | `session_id` / `session_db` / `parent_session_id` | 会话持久化和子 agent 关系 |
| 平台上下文 | `platform` / `user_id` / `chat_id` / `thread_id` / `gateway_session_key` | CLI/Gateway/TUI/ACP 差异 |
| 交互回调 | `tool_progress_callback` / `clarify_callback` / `stream_delta_callback` / `reasoning_callback` | 将 agent 内部事件回传给不同 UI |
| 预算与容错 | `max_iterations` / `iteration_budget` / `fallback_model` / `credential_pool` | 控制 tool loop、fallback 和凭证轮换 |
| 上下文策略 | `ephemeral_system_prompt` / `prefill_messages` / `skip_context_files` / `skip_memory` | 控制 prompt 组成和缓存影响 |

### 多入口创建 `AIAgent` 的差异

| 入口 | 创建位置 | 典型差异 |
|---|---|---|
| Classic CLI | `cli.py` `HermesCLI` 内部 | `platform="cli"`，带 rich/prompt_toolkit 回调、session_db、clarify callback |
| TUI | `tui_gateway/server.py::_make_agent()` | `platform="tui"`，quiet，事件通过 JSON-RPC 发给 Ink UI |
| Gateway | `gateway/run.py` | `platform=<platform_key>`，带 user/chat/thread 元信息，复用 agent cache 保护 prompt cache |
| ACP | `acp_adapter/session.py` | `platform="acp"`，默认 `enabled_toolsets=["hermes-acp"]`，stdout 必须保持协议纯净 |
| Cron | `cron/scheduler.py` | `platform="cron"`，禁用 `cronjob/messaging/clarify`，`skip_memory=True` 防止污染用户表征 |
| Batch | `batch_runner.py` | 面向批处理轨迹生成 |

这个设计的重点是：不同入口只负责 **平台语义和 UI 回调**，核心 tool-use loop 仍然复用 `AIAgent`。

## 五、工具系统：注册、分组、分发

工具系统由三层组成：

```text
tools/*.py
  -> 顶层 registry.register(...)
  -> tools/registry.py 自动发现并 import
  -> registry 保存 ToolEntry(schema, handler, toolset, check_fn)
  -> toolsets.py 定义 toolset 分组
  -> model_tools.py 生成 LLM tool schemas
  -> handle_function_call()
  -> registry.dispatch()
```

### 1. `tools/registry.py`

`tools/registry.py` 没有反向依赖 core，是工具系统最底层。

自动发现逻辑有一个重要细节：它不会简单 import `tools/` 下所有文件，而是用 AST 检查模块顶层是否有 `registry.register(...)` 调用。这样可以避免 helper 模块被误 import，降低副作用。

每个工具最终注册成 `ToolEntry`：

- `name`
- `toolset`
- `schema`
- `handler`
- `check_fn`
- `requires_env`
- `is_async`
- `emoji`
- `max_result_size_chars`

### 2. `model_tools.py`

`model_tools.handle_function_call()` 是模型 tool call 的主分发器。它做的事情不只是调用 handler：

- 按 schema 尝试把字符串参数转换成 number/bool。
- 拦截 agent-loop-only tools，防止普通 registry dispatch。
- 触发插件 `pre_tool_call`，允许插件 block。
- 维护 read/search tool 连续调用计数。
- 对 `execute_code` 注入当前启用工具集合，防止 subagent 污染父 agent toolset。
- 记录 dispatch latency。
- 触发 `post_tool_call` 和 `transform_tool_result` hooks。

所以工具调用路径本身也是插件系统的重要 hook 点。

### 3. `toolsets.py`

`toolsets.py` 是工具暴露策略层。它决定哪些工具属于核心工具、CLI 工具、Gateway 工具、MCP 工具等集合。

Hermes 的工具不是“注册即全部暴露”，而是注册后再由 toolset + config + platform 决定最终 schema。

## 六、状态与路径：`HERMES_HOME` 是边界

Hermes 的状态都围绕 `HERMES_HOME`：

- `config.yaml`
- `.env`
- logs
- sessions
- skills
- plugins
- memory/cache/checkpoints

`hermes_constants.py` 提供两个核心 API：

- `get_hermes_home()`：代码内部使用，返回真实 `Path`。
- `display_hermes_home()`：用户可见输出使用，返回 `~/.hermes` 或 `~/.hermes/profiles/<name>` 这种可读形式。

profile 模式通过 `HERMES_HOME=<root>/profiles/<name>` 实现隔离。注意 profile 操作本身看的是 root，而不是当前 profile home，这样 `hermes -p coder profile list` 仍能看到所有 profiles。

## 七、Classic CLI

Classic CLI 的主体是 `cli.py` 里的 `HermesCLI`。

`cli.main()` 负责：

- 处理 `--gateway` 特殊模式。
- 处理 worktree 隔离。
- 解析 `--toolsets` / `--skills`。
- 创建 `HermesCLI` 实例。
- 单 query 或 interactive run。

`HermesCLI` 创建 `AIAgent` 时传入：

- CLI runtime provider 信息。
- `enabled_toolsets`。
- `ephemeral_system_prompt`。
- `session_db`。
- `clarify_callback`。
- tool progress / tool start / tool complete / stream delta 回调。
- `platform="cli"`。

因此 CLI 层主要解决的是：

- 输入读取。
- slash command 分发。
- rich/prompt_toolkit 展示。
- 工具进度、reasoning、streaming 的终端呈现。
- 本地会话 resume / compact / retry / undo 等交互。

## 八、TUI 与 Dashboard

TUI 是一个双进程架构：

```text
Node Ink UI
  -> stdio JSON-RPC
  -> Python tui_gateway/server.py
  -> AIAgent
```

`tui_gateway/server.py::_make_agent()` 创建 `AIAgent`：

- `platform="tui"`
- `quiet_mode=True`
- 从 config/runtime provider 解析模型和凭证。
- 使用 `_agent_cbs(sid)` 把 tool progress、message delta、approval 等事件发回前端。

Dashboard 的 `/chat` 不重写聊天 UI，而是通过 PTY 嵌入真实 TUI：

```text
web/src/pages/ChatPage.tsx
  -> xterm.js
  -> /api/pty websocket
  -> hermes_cli/pty_bridge.py
  -> child process: hermes --tui
```

这个设计保证 dashboard 和终端 TUI 共享同一套 transcript、composer、slash command 行为。React 侧只做外围结构化 UI，不复制主聊天体验。

## 九、Gateway 多平台消息系统

Gateway 的主体是 `gateway/run.py::GatewayRunner` 和 `gateway/platforms/base.py::BasePlatformAdapter`。

典型消息路径：

```text
平台 adapter
  -> webhook / polling / websocket 收到消息
  -> 生成 MessageEvent
  -> BasePlatformAdapter.handle_message()
  -> active-session guard / pending queue
  -> GatewayRunner._handle_message()
  -> slash/control command 优先处理
  -> GatewayRunner._handle_message_with_agent()
  -> AIAgent.run_conversation()
  -> GatewayStreamConsumer / delivery
  -> 平台 adapter.send()
```

Gateway 创建 `AIAgent` 时会注入：

- `platform=<platform_key>`
- `user_id/user_name/chat_id/chat_name/chat_type/thread_id`
- `gateway_session_key`
- `session_db`
- `fallback_model`
- Gateway 专用 callbacks

一个关键设计点：Gateway 会缓存每个 session 的 `AIAgent`，并用配置签名判断能否复用。这是为了保持冻结的 system prompt 和 tool schemas，从而尽量不破坏 prompt caching。

## 十、ACP 与 MCP

### ACP

ACP 入口由 `hermes acp` 触发，最终在 `acp_adapter/session.py` 创建 agent：

- `platform="acp"`
- 默认 `enabled_toolsets=["hermes-acp"]`
- 可扩展 session MCP servers
- 将普通输出导向 stderr，确保 stdout 保持 ACP JSON-RPC 协议纯净

ACP 更像是 IDE 集成壳，核心执行仍交给 `AIAgent`。

### MCP Server

`mcp_serve.py` 是 Hermes 作为 MCP server 的入口。

它不是直接创建 `AIAgent` 的聊天入口，而是把 Hermes messaging 能力暴露给其他 MCP client，例如：

- `conversations_list`
- `conversation_get`
- `messages_read`
- `attachments_fetch`
- `events_poll`
- `events_wait`
- `messages_send`
- `channels_list`
- `permissions_list_open`
- `permissions_respond`

也就是说，MCP server 主要桥接 Gateway/session store/send_message，而不是提供一个新的本地 agent loop。

## 十一、Cron

`cron/scheduler.py` 会在 job 到期时创建 `AIAgent`：

- `platform="cron"`
- `skip_memory=True`，避免定时任务 system prompt 污染用户记忆表征。
- `load_soul_identity=True`，仍继承用户 SOUL identity。
- 如果 job 有 workdir，则允许加载项目上下文文件。
- 禁用 `cronjob` / `messaging` / `clarify` toolsets，避免递归调度或无人值守时卡在澄清问题。

这说明 Cron 是一个后台 agent runner，而不是单纯 shell 定时器。

## 十二、扩展面

Hermes 的扩展面主要有四类：

| 扩展面 | 目录/文件 | 说明 |
|---|---|---|
| Tools | `tools/*.py` | 通过 `registry.register()` 注册给 LLM 调用 |
| Tool environments | `tools/environments/` | terminal/code execution 的后端:local/docker/ssh/modal/daytona/singularity/**vercel_sandbox**(共 7 种,verified 2026-05-15) |
| Skills | `skills/` / `optional-skills/` | procedural memory，影响 agent 如何完成任务 |
| Plugins | `hermes_cli/plugins.py` / `plugins/` | hooks、tools、CLI commands、platform adapters |
| Gateway platforms | `gateway/platforms/` | 新消息平台适配器 |
| Memory providers | `plugins/memory/` | 长期记忆后端插件 |
| Context/image providers | `plugins/context_engine/` / `plugins/image_gen/` | 专用能力插件 |

这里要注意：插件可以注册工具，但普通工具系统不等于插件系统。内置工具通过 repo 文件自动发现；插件工具通过 `PluginContext.register_tool()` 进入同一个 registry。

## 十三、与 Claude Code / OpenClaw 的对比切入点

### 类似 Claude Code 的部分

- slash commands。
- skills。
- TUI / terminal-first 交互。
- tool-use loop。
- prompt caching 保护。
- context compression。
- Claude Code OAuth credential 兼容。

### 类似 OpenClaw 的部分

- 多平台 messaging gateway。
- session routing。
- OpenClaw migration。
- MCP channel bridge 类能力。
- gateway hooks / platform adapters。
- profile 和长期运行服务场景。

### Hermes 自己更突出的部分

- CLI、TUI、Gateway、ACP、Cron 多入口共用同一 `AIAgent`。
- 工具后端覆盖 local/docker/ssh/modal/daytona/singularity/**vercel_sandbox**(共 7 种,verified 2026-05-15)。
- repo 内置 skills + optional skills + skill hub。
- profile-aware 多实例隔离。
- Gateway agent cache 明确服务 prompt caching。

## 十四、第一轮结论

Hermes 的架构可以简化成一句话：

> 多个产品入口把用户事件标准化成 agent turn，统一交给 `AIAgent`；`AIAgent` 通过 provider transport 调模型，通过 registry/toolsets 调工具，通过 session/memory 保存状态，再由入口层把回调事件渲染或投递回用户。

后续阅读优先级应该是：

1. `run_agent.py`：理解真正的 agent loop。
2. `model_tools.py` + `tools/registry.py` + `toolsets.py`：理解 agent 能做什么。
3. `agent/transports/` + provider adapters：理解模型调用如何被统一。
4. `hermes_state.py` + memory manager：理解状态如何跨轮次保留。
5. `gateway/run.py`：理解长驻多平台异步场景如何包住同步 agent core。

## 待验证问题

- `run_agent.py` 内部是否已经形成明确的“外层容错 + 内层 tool loop”边界，还是混在同一个大循环中。
- CLI/TUI/Gateway 的 session 历史格式是否完全一致。
- Gateway agent cache 在哪些配置变化下会失效。
- MCP dynamic tools 如何影响 prompt cache。
- Skills 在不同入口的加载时机是否一致。
