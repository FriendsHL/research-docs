# 插件与扩展系统源码解析

## 1. 先说结论

Hermes 的插件系统不是只有一种。

它至少有六类扩展面：

```text
1. 通用插件
   注册工具、hook、slash command、CLI 子命令、gateway platform 等。

2. Memory provider 插件
   给 agent 接外部长期记忆系统。

3. Context engine 插件
   替换或扩展上下文压缩/上下文管理引擎。

4. Image generation backend 插件
   给 image_generate 工具接不同图片生成后端。

5. Gateway platform 插件
   新增 IRC、Teams 这类消息平台 adapter。

6. Dashboard 插件
   给 Web Dashboard 增加页面、slot、后端 API。
```

一句话：

```text
通用 PluginManager 负责“工具/hook/命令/平台”。
memory/context/image/dashboard 有各自更专门的发现和激活路径。
```

这点很重要。

如果看到 `plugins/` 目录下的代码，不要默认它们都走同一个 loader。

## 2. 关键文件

| 文件 | 作用 |
|---|---|
| `hermes_cli/plugins.py` | 通用插件系统核心，`PluginManager` / `PluginContext` |
| `hermes_cli/plugins_cmd.py` | `hermes plugins install/list/enable/disable` |
| `plugins/` | repo 内置插件目录 |
| `plugins/memory/__init__.py` | memory provider 专用发现器 |
| `agent/memory_provider.py` | memory provider 抽象类 |
| `agent/memory_manager.py` | built-in memory + 外部 memory provider 调度 |
| `plugins/context_engine/__init__.py` | context engine 专用发现器 |
| `agent/context_engine.py` | context engine 抽象/压缩接口 |
| `agent/image_gen_provider.py` | image generation provider 抽象类 |
| `agent/image_gen_registry.py` | image provider 注册表 |
| `plugins/image_gen/*` | 内置图片生成 backend |
| `plugins/platforms/*` | gateway platform 插件 |
| `hermes_cli/web_server.py` | dashboard 插件 manifest/API/static asset |
| `web/src/plugins/*` | dashboard 前端插件 SDK/registry/slot |
| `model_tools.py` | tool hook 调用点 |
| `run_agent.py` | LLM/session hook 调用点 |

## 4. 通用插件系统是什么

核心在 `hermes_cli/plugins.py`。

通用插件加载后，会调用插件里的：

```python
def register(ctx):
    ...
```

`ctx` 是 `PluginContext`。

插件通过它注册能力：

```text
ctx.register_tool(...)
ctx.register_hook(...)
ctx.register_command(...)
ctx.register_cli_command(...)
ctx.register_platform(...)
ctx.register_context_engine(...)
ctx.register_image_gen_provider(...)
ctx.register_skill(...)
```

所以插件不能随便改 core 文件。

它应该通过这些扩展点接进来。

## 5. 插件从哪里发现

`PluginManager.discover_and_load()` 会扫四类来源：

```text
1. Bundled plugins
   <repo>/plugins/<name>/

2. User plugins
   HERMES_HOME/plugins/<name>/

3. Project plugins
   ./.hermes/plugins/<name>/
   只有 HERMES_ENABLE_PROJECT_PLUGINS 开启才扫

4. Pip entry point plugins
   hermes_agent.plugins entry-point group
```

优先级是后面的覆盖前面的。

也就是说：

```text
project plugin > user plugin > bundled plugin
```

但项目插件默认不开。

因为项目目录里的代码不一定可信。

## 6. plugin.yaml 里有什么

`plugin.yaml` 会被解析成 `PluginManifest`。

常见字段：

```yaml
name: disk-cleanup
version: 2.0.0
description: "Auto-track and clean up ephemeral files"
author: NousResearch
kind: standalone
requires_env:
  - SOME_API_KEY
hooks:
  - post_tool_call
  - on_session_end
```

其中 `kind` 很关键。

## 7. 插件 kind

通用插件系统认识几种 kind：

```text
standalone
  普通插件。默认需要 plugins.enabled 显式启用。

backend
  某个核心工具的后端，比如 image_gen/openai。
  bundled backend 自动加载。

exclusive
  同一类只能启用一个，比如 memory provider。
  不走通用 loader 激活，由专用系统选择。

platform
  gateway 平台 adapter，比如 IRC。
  bundled platform 自动加载。
```

例子：

```yaml
name: openai
kind: backend
```

表示它是一个 backend provider，不是普通用户插件。

## 8. 哪些插件会自动加载

规则可以简单记：

```text
bundled backend
  自动加载

bundled platform
  自动加载

standalone
  默认不加载，需要 plugins.enabled

user-installed plugin
  默认不加载，需要 plugins.enabled

exclusive
  通用 loader 只记录，不加载
```

为什么 standalone 默认 opt-in？

因为插件是 Python 代码。

加载插件就等于执行插件代码。

所以第三方插件不能默认执行。

## 9. 启用和禁用插件

用户命令在 `hermes_cli/plugins_cmd.py`：

```bash
hermes plugins list
hermes plugins enable disk-cleanup
hermes plugins disable disk-cleanup
hermes plugins install owner/repo
hermes plugins remove my-plugin
```

启用状态写在：

```yaml
plugins:
  enabled:
    - disk-cleanup
  disabled:
    - some-old-plugin
```

`disabled` 优先级更高。

如果同一个插件同时在 enabled 和 disabled：

```text
disabled 赢。
```

## 10. PluginManager 里存什么

`PluginManager` 主要有这些状态：

```text
_plugins
  key -> LoadedPlugin

_hooks
  hook_name -> callback list

_plugin_tool_names
  插件注册过的工具名

_plugin_platform_names
  插件注册过的平台名

_cli_commands
  hermes <subcommand> 级别的 CLI 命令

_plugin_commands
  会话里的 slash command

_context_engine
  插件注册的 context engine

_plugin_skills
  插件提供的只读 skill
```

`LoadedPlugin` 记录：

```text
manifest
module
tools_registered
hooks_registered
commands_registered
enabled
error
```

所以 `hermes plugins list` 能看到插件是否加载成功、错误是什么。

## 11. 插件怎么注册工具

插件调用：

```python
ctx.register_tool(
    name="spotify_search",
    toolset="spotify",
    schema=SPOTIFY_SEARCH_SCHEMA,
    handler=_handle_spotify_search,
    check_fn=_check_spotify_available,
)
```

`PluginContext.register_tool()` 内部直接调用：

```text
tools.registry.register(...)
```

所以插件工具和内置工具最终在同一个 registry 里。

模型看到的仍然是普通 tool schema。

主循环也不需要关心这个工具来自插件还是内置。

## 12. Spotify 插件例子

`plugins/spotify/__init__.py` 是一个很直观的例子。

它注册 7 个工具：

```text
spotify_playback
spotify_devices
spotify_queue
spotify_search
spotify_playlists
spotify_albums
spotify_library
```

都放在：

```text
toolset="spotify"
```

并且有：

```text
check_fn=_check_spotify_available
```

这意味着：

```text
工具可以被注册。
但如果用户没配 Spotify auth，运行时会不可用。
```

这样 `hermes tools` 还能展示这个工具集，让用户知道可以配置。

## 13. 插件怎么注册 slash command

插件调用：

```python
ctx.register_command(
    "disk-cleanup",
    handler=_handle_slash,
    description="Track and clean up ephemeral Hermes session files.",
)
```

这注册的是会话里的命令：

```text
/disk-cleanup
```

不是：

```text
hermes disk-cleanup
```

两者不同：

```text
register_command
  会话里的 slash command

register_cli_command
  终端命令行里的 hermes <subcommand>
```

插件 slash command 会进入：

```text
_plugin_commands
```

之后 CLI / gateway 可以通过插件命令分发逻辑调用它。

## 14. 插件怎么注册 CLI 子命令

如果插件想加：

```bash
hermes myplugin ...
```

它用：

```python
ctx.register_cli_command(
    name="myplugin",
    help="...",
    setup_fn=setup_argparse,
    handler_fn=handler,
)
```

`setup_fn` 会拿到 argparse subparser。

这适合：

- 登录流程
- 安装/配置向导
- provider 管理命令
- 离线维护命令

和会话 slash command 不一样。

## 15. hook 是什么

hook 就是 core 在关键点喊一声：

```text
现在要调用工具了，有插件想看一下吗？
现在工具调用完了，有插件想记录一下吗？
现在要发模型请求了，有插件想注入上下文吗？
现在 session 开始/结束了，有插件想做清理吗？
```

插件注册：

```python
ctx.register_hook("post_tool_call", callback)
```

core 调用：

```python
invoke_hook("post_tool_call", ...)
```

所有 callback 都会被 try/except 包起来。

一个插件报错，不会弄崩主循环。

## 16. 支持哪些 hook

`VALID_HOOKS` 里有：

```text
pre_tool_call
post_tool_call
transform_terminal_output
transform_tool_result
pre_llm_call
post_llm_call
pre_api_request
post_api_request
on_session_start
on_session_end
on_session_finalize
on_session_reset
subagent_stop
pre_gateway_dispatch
pre_approval_request
post_approval_response
```

这些 hook 分几类：

```text
工具类
  pre_tool_call / post_tool_call / transform_tool_result

模型类
  pre_llm_call / post_llm_call / pre_api_request / post_api_request

session 生命周期
  on_session_start / on_session_end / on_session_finalize / on_session_reset

gateway
  pre_gateway_dispatch

approval
  pre_approval_request / post_approval_response
```

## 17. pre_tool_call 可以阻止工具

`pre_tool_call` 比普通观察 hook 更强。

插件可以返回：

```python
{
    "action": "block",
    "message": "这个工具被策略禁止"
}
```

`get_pre_tool_call_block_message()` 会取第一个 block。

然后工具不会执行。

模型收到的是：

```json
{"error": "这个工具被策略禁止"}
```

例子：

```text
插件禁止 terminal 执行 rm -rf
  -> pre_tool_call 返回 block
  -> terminal 不执行
  -> 工具结果变成 error
  -> 模型需要换一种做法或解释给用户
```

## 18. 工具 hook 调用点

`model_tools.handle_function_call()` 里有工具 hook。

大概流程：

```text
handle_function_call(function_name, args)
  -> coerce args
  -> pre_tool_call hook
  -> 如果 block，直接返回 error
  -> registry.dispatch(...)
  -> post_tool_call hook
  -> transform_tool_result hook
  -> 返回结果给 agent loop
```

`post_tool_call` 会拿到：

```text
tool_name
args
result
task_id
session_id
tool_call_id
duration_ms
```

`duration_ms` 很实用。

观测插件可以用它做：

- 慢工具告警
- 成本统计
- dashboard 图表
- 调试日志

## 19. transform_tool_result 可以改工具结果

`post_tool_call` 是观察。

`transform_tool_result` 可以返回新的字符串结果。

流程是：

```text
工具原始 result
  -> post_tool_call 观察
  -> transform_tool_result 可替换
  -> 替换后的 result 进入模型上下文
```

例子：

```text
某个工具输出里有内部路径或 token
  -> transform_tool_result 把敏感字段打码
  -> 模型只看到脱敏版本
```

如果多个插件都返回字符串：

```text
第一个有效字符串 wins。
```

## 20. pre_llm_call 怎么注入上下文

`run_agent.py` 在进入主 tool loop 前调用：

```text
pre_llm_call
```

插件可以返回：

```python
{"context": "这里是插件召回的上下文"}
```

或者直接返回字符串：

```python
"这里是插件召回的上下文"
```

这些内容会被注入到当前轮 user message。

注意：

```text
不是注入 system prompt。
```

原因是 prompt caching。

system prompt 要尽量保持稳定，否则缓存会失效。

所以插件上下文是：

```text
API-call-time 临时注入
不写入 SessionDB
不改变系统提示词
```

## 21. post_llm_call 做什么

`post_llm_call` 在一轮完成后触发。

它能拿到：

```text
session_id
user_message
assistant_response
conversation_history
model
platform
```

适合做：

- 外部追踪
- 数据同步
- 统计
- 生成摘要
- 观测日志

比如 Langfuse 插件就会注册：

```text
pre_api_request
post_api_request
pre_llm_call
post_llm_call
pre_tool_call
post_tool_call
```

用来记录 LLM 和工具 trace。

## 22. session hook

`on_session_start`：

```text
新 session 第一次构建 system prompt 时触发。
```

适合初始化 session-scoped 状态。

`on_session_end`：

```text
每次 run_conversation 结束时触发。
```

注意这里名字容易误解。

它不是“用户彻底退出 session”才触发。

在当前代码里，它在每次 `run_conversation()` 末尾都会触发。

所以如果插件要做昂贵清理，要自己判断频率。

## 23. disk-cleanup 插件例子

`plugins/disk-cleanup` 是一个好例子。

它注册：

```python
ctx.register_hook("post_tool_call", _on_post_tool_call)
ctx.register_hook("on_session_end", _on_session_end)
ctx.register_command("disk-cleanup", ...)
```

它做的事情：

```text
1. 监听 write_file / patch / terminal 工具。
2. 从 args 或输出里找新建的临时文件路径。
3. 判断是不是 test/temp/research/download 等可清理类型。
4. 记录到 HERMES_HOME 范围内的追踪文件。
5. 在 on_session_end 时自动 quick cleanup。
6. 用户也可以手动 /disk-cleanup status 或 /disk-cleanup quick。
```

例子：

```text
agent 写了 /tmp/hermes-abc/test_tmp.py
  -> post_tool_call 捕获 write_file args.path
  -> disk-cleanup 记录为 test 文件
  -> turn 结束
  -> on_session_end 自动清掉
```

这里 agent 自己不需要记得清理。

插件通过 hook 做了。

## 24. pre_gateway_dispatch

Gateway 收到平台消息后，可以在进入鉴权和 agent 分发前触发：

```text
pre_gateway_dispatch
```

插件可以返回：

```python
{"action": "skip", "reason": "..."}
```

表示丢掉这条消息。

也可以返回：

```python
{"action": "rewrite", "text": "..."}
```

表示改写消息文本后继续。

例子：

```text
插件看到 Telegram 群里没有 @bot 的普通闲聊
  -> skip

插件看到企业微信消息里有内部 ticket URL
  -> rewrite 成更适合 agent 的文本
```

## 25. approval hook

approval hooks 是观察型。

包括：

```text
pre_approval_request
post_approval_response
```

它们会在危险命令需要审批时触发。

但注意：

```text
不能通过这些 hook 自动同意或拒绝审批。
返回值会被忽略。
```

如果插件要阻止某类操作，应该用：

```text
pre_tool_call
```

在进入 approval 之前 block。

## 26. Memory provider 插件为什么单独做

Memory provider 不是普通通用插件。

原因：

```text
同一时间只能有一个外部 memory provider。
```

如果同时加载 Honcho、Mem0、Supermemory、Hindsight：

- 工具 schema 会膨胀
- 多个后端可能写入冲突
- 系统提示词会变复杂
- recall 结果可能互相打架

所以 memory 有专用体系：

```text
plugins/memory/__init__.py
  -> discover_memory_providers()
  -> load_memory_provider(name)

agent/memory_manager.py
  -> built-in provider always on
  -> at most one external provider
```

激活靠：

```yaml
memory:
  provider: honcho
```

而不是 `plugins.enabled`。

## 27. MemoryProvider 接口

`agent/memory_provider.py` 定义抽象类。

核心方法：

```text
is_available()
initialize(session_id, hermes_home, platform, ...)
system_prompt_block()
prefetch(query)
queue_prefetch(query)
sync_turn(user, assistant)
get_tool_schemas()
handle_tool_call(tool_name, args)
shutdown()
```

可选 hook：

```text
on_turn_start
on_session_end
on_session_switch
on_pre_compress
on_memory_write
on_delegation
```

这些不是通用 PluginManager hook。

它们是 MemoryManager 调 provider 的方法。

## 28. MemoryManager 怎么调度

`MemoryManager` 里一定有 built-in provider。

然后最多加一个外部 provider。

它做几件事：

```text
build_system_prompt()
  收集 provider 的静态 system prompt block

prefetch_all(query)
  当前轮开始前召回相关记忆

queue_prefetch_all(query)
  当前轮结束后为下一轮预热召回

sync_all(user, assistant)
  当前轮结束后同步到外部记忆

get_all_tool_schemas()
  收集 memory provider 暴露的工具

handle_tool_call(...)
  把 memory 工具路由到对应 provider
```

所有 provider 调用基本都是 fail-open。

一个外部记忆服务失败，不应该让 agent 整轮崩掉。

## 29. Memory 插件例子

假设配置：

```yaml
memory:
  provider: mem0
```

一轮对话大概是：

```text
agent init
  -> load_memory_provider("mem0")
  -> provider.is_available()
  -> memory_manager.add_provider(mem0)
  -> memory_manager.initialize_all(session_id, hermes_home, platform)

用户发消息
  -> memory_manager.on_turn_start(...)
  -> memory_manager.prefetch_all(user_message)
  -> 把召回内容包成 <memory-context> 注入 user message

assistant 完成
  -> memory_manager.sync_all(user, assistant)
  -> memory_manager.queue_prefetch_all(user)
```

注意：

```text
prefetch 是当前轮用。
queue_prefetch 是给下一轮预热。
```

## 30. memory context 为什么要包标签

`MemoryManager.build_memory_context_block()` 会把召回内容包成：

```text
<memory-context>
[System note: The following is recalled memory context, NOT new user input...]

...
</memory-context>
```

这告诉模型：

```text
这是背景记忆，不是用户的新指令。
```

同时 streaming 输出里还有 scrubber。

如果模型不小心把 `<memory-context>` 内容吐出来，`StreamingContextScrubber` 会尽量在流式输出里清掉。

## 31. Context engine 插件

Context engine 也有专用发现器：

```text
plugins/context_engine/__init__.py
```

它扫：

```text
plugins/context_engine/<name>/
```

只允许一个 active engine。

选择靠：

```yaml
context:
  engine: xxx
```

默认是内置 compressor。

context engine 插件可以用两种形式：

```text
1. register(ctx)，调用 ctx.register_context_engine(engine)
2. 定义 ContextEngine 子类，发现器实例化它
```

这类插件用于替换上下文管理/压缩逻辑。

## 32. Image generation backend 插件

图片生成也是 provider 模式。

抽象类：

```text
agent/image_gen_provider.py
```

注册表：

```text
agent/image_gen_registry.py
```

插件调用：

```python
ctx.register_image_gen_provider(OpenAIImageGenProvider())
```

然后 `image_generate` 工具会根据：

```yaml
image_gen:
  provider: openai
```

找到 active provider。

如果没有配置：

```text
1. 只有一个 provider，使用它。
2. 否则优先 fal。
3. 否则返回 None，让工具提示用户配置。
```

## 33. Image provider 例子：OpenAI

`plugins/image_gen/openai` 是 bundled backend。

`plugin.yaml`：

```yaml
name: openai
kind: backend
requires_env:
  - OPENAI_API_KEY
```

`register(ctx)`：

```python
ctx.register_image_gen_provider(OpenAIImageGenProvider())
```

provider 的 `generate()` 会：

```text
1. 检查 prompt。
2. 检查 OPENAI_API_KEY。
3. import openai。
4. 解析 image_gen.openai.model / image_gen.model。
5. 调 OpenAI images.generate。
6. 如果返回 b64，保存到 HERMES_HOME/cache/images。
7. 返回统一 success_response。
```

所以 image_generate 工具本身不需要知道 OpenAI 的细节。

它只调 active provider。

## 34. Gateway platform 插件

platform 插件用：

```python
ctx.register_platform(...)
```

例子是：

```text
plugins/platforms/irc
```

它注册：

```python
ctx.register_platform(
    name="irc",
    label="IRC",
    adapter_factory=lambda cfg: IRCAdapter(cfg),
    check_fn=check_requirements,
    validate_config=validate_config,
    required_env=["IRC_SERVER", "IRC_CHANNEL", "IRC_NICKNAME"],
    setup_fn=interactive_setup,
    ...
)
```

注册后进入：

```text
gateway.platform_registry
```

Gateway 启动平台时，就能像内置平台一样发现 IRC。

## 35. Gateway platform 插件例子

IRC adapter 继承：

```text
BasePlatformAdapter
```

它自己实现：

- connect
- disconnect
- receive loop
- send message
- session source 生成
- IRC message parse
- allowlist
- 平台提示词 hint

## 36. Dashboard 插件

Dashboard 插件不是 `PluginManager` 的 Python hook 系统。


如果 manifest 声明了：




## 37. Dashboard 前端插件怎么加载

```text
3. 加载 /dashboard-plugins/<name>/<entry> script。
4. 等插件调用 window.__HERMES_PLUGINS__.register(...)。
```

插件 JS 不需要自己 bundle React。

## 38. Dashboard slot

Dashboard 插件可以注册整页：

```javascript
window.__HERMES_PLUGINS__.register("example", ExamplePage)
```

也可以注册 slot：

```javascript
window.__HERMES_PLUGINS__.registerSlot(
  "example",
  "sessions:top",

```

slot 是页面里的插槽。

例如：

```text

sidebar

```

这让插件不用覆盖整个页面，也能往页面里加小组件。

## 39. 插件和 prompt caching 的关系

插件最容易破坏 prompt cache 的地方是：

```text
改变 system prompt
改变工具列表
改变历史消息
```

Hermes 的设计是：

```text
pre_llm_call 注入 user message，不改 system prompt。
plugin context 是临时的，不写入 DB。
工具集变化需要显式 reload 或初始化时完成。
```

比如 `/reload-mcp` 会提示 prompt cache invalidation。

同理，如果插件中途注册/移除工具，也会让 tool schema 改变。

这类事情应该尽量发生在 session 开始前，或者明确告诉用户会失效。

## 40. 插件加载时机的坑

通用插件发现经常依赖：

```text
model_tools.py import 副作用
```

因为工具系统和插件工具都在那里交汇。

AGENTS 里也提醒：

```text
discover_plugins() only runs as a side effect of importing model_tools.py
```

所以如果某条代码路径想读取 plugin state，但没 import `model_tools.py`，可能看不到插件。

正确做法：

```text
显式调用 discover_plugins()
```

这个函数是 idempotent。

重复调用一般不会重复加载，除非：

```python
discover_plugins(force=True)
```

## 41. 一个完整例子：disk-cleanup 怎么挂进 agent loop

用户启用：

```bash
hermes plugins enable disk-cleanup
```

然后 agent 做任务：

```text
请写一个临时测试脚本验证这个函数
```

流程：

```text
1. PluginManager 发现 disk-cleanup。
2. 调用 disk-cleanup.register(ctx)。
3. 插件注册 post_tool_call / on_session_end / slash command。
4. 模型调用 write_file 写 /tmp/hermes-xxx/test_foo.py。
5. model_tools.handle_function_call 执行 write_file。
6. 执行后 invoke_hook("post_tool_call", ...）。
7. disk-cleanup 从 args.path 识别 test 文件并 track。
8. turn 结束，run_agent 调 invoke_hook("on_session_end", ...）。
9. disk-cleanup quick cleanup。
10. 用户也可以运行 /disk-cleanup status 查看。
```

这就是插件最典型的价值：

```text
不改 agent 主循环。
不要求模型记住清理。
通过 hook 在关键点补行为。
```

## 42. 一个完整例子：新增一个工具插件

假设插件想加一个天气工具。

结构：

```text
~/.hermes/plugins/weather/
  plugin.yaml
  __init__.py
```

`plugin.yaml`：

```yaml
name: weather
version: 1.0.0
description: "Weather lookup tools"
requires_env:
  - WEATHER_API_KEY
```

`__init__.py`：

```python
import json

def _check():
    import os
    return bool(os.getenv("WEATHER_API_KEY"))

def _handle(args, **kwargs):
    city = args.get("city", "")
    return json.dumps({"city": city, "forecast": "sunny"})

def register(ctx):
    ctx.register_tool(
        name="weather_lookup",
        toolset="weather",
        schema={
            "name": "weather_lookup",
            "description": "Look up weather for a city",
            "parameters": {
                "type": "object",
                "properties": {
                    "city": {"type": "string"}
                },
                "required": ["city"]
            }
        },
        handler=_handle,
        check_fn=_check,
    )
```

然后：

```bash
hermes plugins enable weather
```

下次加载插件后，模型就能看到 `weather_lookup` 工具。

## 43. 一个完整例子：新增 Gateway 平台

如果要加一个新消息平台，比如 `matrix-lite`：

插件可以：

```python
def register(ctx):
    ctx.register_platform(
        name="matrix-lite",
        label="Matrix Lite",
        adapter_factory=lambda cfg: MatrixLiteAdapter(cfg),
        check_fn=lambda: True,
        required_env=["MATRIX_TOKEN"],
        setup_fn=interactive_setup,
    )
```

`MatrixLiteAdapter` 继承：

```text
BasePlatformAdapter
```

实现平台连接和消息转换。

Gateway 不需要硬编码这个平台。

这就是“插件不得修改 core files”的实际含义：

```text
需要新能力时，扩展 register_platform 这类通用面。
不要在 gateway/run.py 里写 matrix-lite 特判。
```

## 44. 设计观察

### 44.1 插件系统的核心是“把不稳定能力移出 core”

Spotify、Google Meet、Langfuse、IRC、Dashboard 扩展都可能变化很快。

它们不适合塞进 agent 主循环。

插件让 core 保持稳定。

### 44.2 专用插件面比万能插件更清楚

memory、context、image_gen 都没有完全走通用 hook。

它们有自己的 ABC 和 registry。

这让约束更明确：

```text
memory 只能一个外部 provider
image_gen 通过 active provider 路由
context engine 只能一个
```

### 44.3 hook 默认 fail-open

插件报错会记录 warning/debug，但不让 agent 崩。

这对用户体验重要。

但插件作者也要注意：

```text
不要把安全策略只写成容易失败的外部服务调用。
```

如果安全策略失败就应该阻止工具，需要在插件内部明确 fail-closed。

### 44.4 插件工具和内置工具共享 registry

好处是 agent loop 简单。

坏处是命名冲突要小心。

`tools.registry` 已经有冲突保护：

```text
不允许插件/MCP 覆盖内置工具。
```

### 44.5 Dashboard 插件是另一套前端生态

Dashboard 插件重点不是 agent loop。

它是：

```text
Web UI 页面/slot/API 扩展。
```

不要把 dashboard 插件和 Python hook 插件混为一谈。

一个插件目录可以同时有：

```text
plugin.yaml + __init__.py
dashboard/manifest.json + dist/index.js + plugin_api.py
```

也就是说它既可以扩展 agent 后端，也可以扩展 dashboard。
