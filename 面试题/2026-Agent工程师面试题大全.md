## 一、基础概念（必考）

### 1.1 Agent 与 LLM/Chatbot 的区别
- **LLM**: 大脑内核，根据输入预测后续文本
- **ChatGPT**: 基于 LLM 优化的对话产品，专注交互层
- **Agent**: LLM + 规划 + 工具 + 记忆，能自主完成多步骤任务
- **核心区别**: Chatbot 只做对话，Agent 有自主规划、工具调用、长期记忆

### 1.2 Agent 核心组件
1. **感知模块**: 处理多模态输入，理解意图
2. **规划模块**: 目标分解、策略制定、资源分配
3. **记忆模块**: 短期记忆(上下文) + 工作记忆(中间结果) + 长期记忆(历史)
4. **执行模块**: 工具调用、外部系统交互
5. **反思模块**: 结果评估、错误处理、经验优化

### 1.3 Workflow / Agent / Tools 区别
| 维度 | Workflow | Agent | Tools |
|------|----------|-------|-------|
| 本质 | 任务编排框架 | 自主决策智能体 | 能力扩展单元 |
| 决策者 | 引擎预设 | AI 自主决策 | 被调用执行 |
| 灵活性 | 低(预设流程) | 高(动态决策) | 无决策能力 |

## 二、Agent 设计范式（高频）

### 2.1 ReAct (Reasoning + Acting)
- **核心思想**: 边想边做，让模型在推理过程中调用工具
- **适用场景**: 知识库问答，需要外部检索的场景
- **实战效果**: 复杂问题分解准确率提升 ~15%

### 2.2 Plan-and-Execute
- **核心思想**: 先规划再执行，先拆解所有步骤再依次执行
- **适用场景**: 步骤明确的复杂任务
- **优点**: 规划清晰，可预览

### 2.3 Reflection (反思机制)
- **核心思想**: 每轮执行后进行自我反思，评估结果
- **使用方式**: 通常叠加在 ReAct 或 Plan-and-Execute 上 (ReAct + Reflection)
- **优点**: 提升不确定环境下的鲁棒性
- **缺点**: 额外 LLM 调用开销

### 2.4 ToT (Tree of Thoughts)
- **核心思想**: 树状搜索多条推理路径
- **优点**: 效果最好
- **缺点**: token 消耗是 CoT 的 3 倍

> **面试加分**: 说清楚每个范式的 trade-off，效果提升多少，成本增加多少

## 三、多轮对话与记忆系统

### 3.1 多轮对话设计
**三种实现方式**:
1. **基于槽位状态机**: 每个意图对应一组必填槽，槽满执行（适合流程固定）
2. **基于 DST**: 用规则/小模型更新对话状态
3. **基于 LLM**: 隐式状态跟踪，靠上下文

**关键点**: 意图置信度判断、低置信度时主动澄清（给选项、追问关键信息）

### 3.2 记忆机制设计
- **短期记忆**: Context Window，受限于 token 数量
- **工作记忆**: 中间结果存储
- **长期记忆**: MEMORY.md / USER.md + SQLite + Skills

**设计要点**:
- 记忆粒度怎么定？
- 记忆是怎么存的？用什么格式？
- 记忆怎么用的？何时检索？

### 3.3 上下文溢出解决方案
- 滑动窗口
- 关键信息提取
- 自动摘要
- 向量检索召回历史

## 四、工具调用（重灾区）

### 4.1 Function Calling 原理
1. LLM 识别用户意图
2. 生成结构化参数
3. 系统调用外部 API
4. LLM 将结果转成自然语言

### 4.2 MCP (Model Context Protocol)
**为什么出现**: 解决不同工具和 LLM 交互混乱的问题

**架构**:
- MCP Host: 用户交互入口 (Claude Desktop, ChatGPT 等)
- MCP Client: 协议转换、安全传输
- MCP Server: 封装外部工具与数据源

**通信方式**:
- 本地进程通信 (文件系统等)
- SSE (远程服务)
- Streamable HTTP (流式交互)

**MCP vs Function Calling**:
| 维度 | MCP | Function Calling |
|------|-----|------------------|
| 定位 | 标准化协议 | LLM 内置功能 |
| 范围 | 多工具、多数据源 | 单个 API 调用 |
| 生态 | 厂商中立 | 依赖模型厂商 |

### 4.3 A2A 协议
- **作用**: Agent 与 Agent 之间的通信规范
- **核心思想**: 用结构化数据(JSON/XML)替代自然语言废话
- **适用场景**: 多 Agent 协作

### 4.4 工具调用失败处理
- 参数格式不对 → 参数校验 + 重试
- 调用后结果不符预期 → 异常处理 + 降级策略
- 权限问题 → 权限校验

## 五、RAG 系统（拉开差距）

### 5.1 RAG 工作流程
1. **数据准备**: 收集→清洗→切分→Embedding→存入向量数据库
2. **查询处理**: 问题→向量→Top-K 检索
3. **信息融合**: 检索文档作为上下文→LLM 生成

### 5.2 文档切分策略
- 固定大小 (chunk_size, chunk_overlap)
- 递归切分 (RecursiveCharacterTextSplitter)
- 语义切分

**面试坑点**: 语义被切断了怎么办？粒度怎么选？

### 5.3 Embedding 模型选型
- 中文: bge-large-zh, text-embedding-v2 (阿里云)
- 英文: bge-large, text-embedding-3-small

**评估指标**: 召回率、准确率

### 5.4 向量数据库
- Milvus, Pinecone, Chroma, Weaviate, Qdrant

### 5.5 检索优化（加分项）
- **Query Rewrite**: 改写查询使其更匹配文档
- **多路召回**: 关键词 + 向量 + BM25
- **Rerank**: 用 bge-reranker-v2-m3 提升 ~20% 准确率
- **Self-RAG**: 自反思检索增强
- **图数据库**: 关系复杂时使用

## 六、幻觉控制与质量评估

### 6.1 幻觉来源
- 训练数据偏见
- 知识截止
- 上下文理解错误

### 6.2 解决方案
1. **限制来源**: 只基于检索结果 / API 返回回答
2. **二次校验**: 对关键结论做验证
3. **Prompt 约束**: 明确写"不确定就说不知道"
4. **引用溯源**: 返回答案时附带来源

### 6.3 评估指标 (RAGAS)
- Faithfulness (忠实度)
- Answer Relevancy (回答相关性)
- Context Precision (上下文精确度)
- Context Recall (上下文召回率)

## 七、系统设计（高频）

### 7.1 设计企业级智能客服 Agent
```
接入层 → 多渠道 (网页/APP/公众号/企微)
   ↓
Agent 核心层 → 规划 / 工具调用 / 反思 / 记忆
   ↓
工具层 → 知识库检索 / 工单系统 API / 用户信息查询 / 物流查询
```

**必答点**:
- 状态追踪 (在哪一步、已有哪些信息)
- 超时/打断处理
- 意图不清时的澄清策略
- 数据传递 (订单号从点餐→支付→售后)
- 失败处理 (重试还是降级)

### 7.2 Agent 平台设计 (大厂常见)
- 智能体平台、工作流编排
- 工具生态、评测系统
- 推理优化、多租户

## 八、大厂真题实例

**Q1: 你做的 Agent 项目里，用了什么框架？为什么选它？它的劣势是什么？如果让你设计会怎么优化？**
- 可能的坑: LangChain 生态完善但过度封装、调试困难

**Q2: 工具调用失败怎么处理？**
- 参数格式、权限、超时、结果校验

**Q3: 上下文溢出怎么办？**
- 滑动窗口、摘要、向量召回

**Q4: ReAct/CoT/ToT 在项目里用过哪个？效果如何？**
- 关键: 量化效果 + 成本分析

**Q5: 怎么通过用户反馈优化 Agent？**
- badcase 收集 → 归因 (意图/检索/生成/工具) → 针对性迭代 → A/B 验证
